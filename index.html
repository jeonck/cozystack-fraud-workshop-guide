Real-time card fraud detection, built step by step

In about two hours you build a working fraud-detection system for card payments on your own private cloud — then run it like a bank runs production: through a traffic spike, a database node failure, and a live server move mid-payment. The legacy switch stays untouched; you build detection around it.

≈ 2 hTotal, 5 parts
20 /sLive payments from terminals
400 msScorer deadline, else stand-in
$5,000The old switch's only rule

A guided walkthrough of the official workshop: aenix-org/cozystack-workshop · fraud/README.md — commands and YAML are quoted from it; replace austinNN with your own username everywhere.

The system at a glance

Every card payment asks one question — approve or decline? The switch used to answer alone. After this workshop, it asks a scorer over Kafka, and every answer is journaled for cases, analytics, and explanations.

Who does what

Piece Runs where Job
SwitchVM in your tenantAnswers terminals; asks the scorer, or decides alone (stand-in)
KafkaCatalog serviceCarries every request, decision and journal entry
RedisCatalog serviceRemembers each card's recent activity: how often, where, how much
PostgreSQLCatalog service, 2 replicasThe case database: every transaction and every alert
Scorer · Cases · DashboardYour Kubernetes clusterDecide, record, show
ExplainerYour Kubernetes clusterQwen2.5 0.5B on CPU writes a plain-language reason for each block
TerminalsYour Kubernetes clusterShops across the US sending ordinary payments

PART 0 Look around 15 min

Goal: know where everything lives — two kubectl contexts, one Git repository — and prove the problem is real before building anything.

1

Log in and find your tenantLaptop → Bastion

SSH into the shared bastion VM and look at the workshop materials. You have two kubectl contexts: tenant talks to Cozystack itself (VM, catalog services, the cluster object); fraud talks to your own Kubernetes cluster, where the detection services will run.

ssh austinNN@<bastion-address>
cd ~/workshop && ls

kubectl --context tenant get vminstances,kubernetes
kubectl --context tenant get resourcequota
kubectl --context tenant get applicationdefinitions
kubectl --context fraud get nodes
kubectl --context fraud -n fraud get pods
✓

The switch VM and cluster fraud are ready, you see your quota (hard = limit, used = consumed), the orderable catalog, one cluster node, and the running terminals pod. A prepull-explainer pod in Completed is expected — the host pre-downloaded the language model. The same objects appear in the Cozystack dashboard under your tenant.

2

Your infrastructure is a Git repositoryBastion · GitLab

Everything the platform runs for you is declared in ~/fraud-infra/platform/. Flux applies that folder from the main branch within about a minute of every push, using your tenant rights. Every service you order in this workshop ends up as a file here — Git is the source of truth.

cd ~/fraud-infra && ls platform && cat platform/kubernetes.yaml
✓

kubernetes.yaml (your fraud cluster) and switch-vm.yaml (the legacy switch). Open the same repo in GitLab: gitlab.workshop.aenix.io/austinNN/fraud-infra — same username and password as the bastion.

3

Watch the bare switch — then attack itBastion · Switch VM

Enter the switch VM console (user ubuntu, password ubuntu), follow its log, then leave with Ctrl-]. Back on the bastion, launch the fraud attack against the undefended switch.

cd ~/workshop
virtctl console vm-instance-switch
# inside the VM:
journalctl -u auth-switch -f
# Ctrl-C to stop the log, Ctrl-] to leave the console

kubectl --context fraud apply -f manifests/04-attack.yaml
kubectl --context fraud -n fraud logs job/attack -f
✓

The log repeats “100 authorizations, 0 declined, stand-in 0.0%, p99 0 ms” — legacy mode declines only amounts above $5,000. The attack log shows card testing, impossible travel and a BIN attack — then “sent 30, approved 30, declined 0”. Every fraudulent payment passes. Remember these cards: in Part 2 the same attack meets your scorer.

PART 1 Order the data services 30 min

Three catalog services, ordered three different ways — that contrast is the lesson. Kafka carries requests, decisions and the journal. Redis remembers each card's recent activity. PostgreSQL stores transactions and alerts, with a primary and a hot standby.

1

Redis: start in the GUI, finish in GitDashboard · Bastion

In the Cozystack dashboard, open your tenant's catalog and create Redis named features: replicas 1, size 1Gi, storage class replicated, authentication off. Then inspect what the GUI created, copy just the declaration fields (apiVersion, kind, metadata.name, the spec fields — never status) into ~/fraud-infra/platform/redis.yaml, and push. From now on Git manages the object the GUI created.

kubectl --context tenant get redis features -o yaml
Solution — platform/redis.yaml 
apiVersion: apps.cozystack.io/v1alpha1
kind: Redis
metadata:
  name: features
spec:
  replicas: 1
  size: 1Gi
  storageClass: replicated
  authEnabled: false
cd ~/fraud-infra
git add platform/redis.yaml
git commit -m "Order Redis for card history"
git push
2

Kafka: write it from the docsBastion · Docs

Using the Cozystack Kafka documentation, write platform/kafka.yaml yourself: one broker, 5Gi on replicated storage, preset c1.small (KRaft mode — no ZooKeeper), and three topics with 8 partitions and 1 replica each. The partition count looks minor now; Part 4 shows it is the ceiling of the whole system.

Solution — platform/kafka.yaml 
apiVersion: apps.cozystack.io/v1alpha1
kind: Kafka
metadata:
  name: kafka
spec:
  kafka:
    replicas: 1
    size: 5Gi
    storageClass: replicated
    resourcesPreset: c1.small
  topics:
    - {name: auth.requests,  partitions: 8, replicas: 1, config: {}}
    - {name: auth.decisions, partitions: 8, replicas: 1, config: {}}
    - {name: auth.journal,   partitions: 8, replicas: 1, config: {}}
auth.requests

The switch's questions to the scorer.

auth.decisions

The scorer's answers back to the switch.

auth.journal

Every answer the switch gave — whoever decided it. The audit trail.

3

PostgreSQL: a primary and a hot standbyBastion · Docs

Write platform/postgres.yaml from the PostgreSQL docs: name cases, replicas: 2 (that means primary plus one standby), 2Gi each on replicated storage, preset t1.micro, user fraud, database fraud owned by that user. Do not set a password — Cozystack generates it into the Secret postgres-cases-credentials; step 2.1 hands it to your services.

Solution — platform/postgres.yaml 
apiVersion: apps.cozystack.io/v1alpha1
kind: Postgres
metadata:
  name: cases
spec:
  replicas: 2
  size: 2Gi
  storageClass: replicated
  resourcesPreset: t1.micro
  users:
    fraud: {}
  databases:
    fraud:
      roles:
        admin: [fraud]
4

Commit, push, and watch them come upBastion

cd ~/fraud-infra
git add platform/kafka.yaml platform/postgres.yaml
git commit -m "Order Kafka and the case database"
git push

watch -n 5 kubectl --context tenant get kafka,redis,postgres
✓

Redis and PostgreSQL reach READY True in one or two minutes; Kafka takes ten to twenty. When the whole room orders at once, the platform installs services one after another. You can start Part 2 as soon as Redis and PostgreSQL are ready — the fraud services wait for Kafka by themselves.

5

Under the hood: operators do the workBastion

Look at what your three short declarations became. Cozystack turns each application into Helm releases and operator resources; Strimzi runs Kafka, CloudNativePG runs PostgreSQL, and the Redis operator runs Redis — keeping pods and services healthy underneath.

kubectl --context tenant get hr
kubectl --context tenant get clusters.postgresql.cnpg.io
kubectl --context tenant get pods -l cnpg.io/cluster=postgres-cases -L role
kubectl --context tenant get svc | grep postgres-cases
✓

Helm releases, the CloudNativePG cluster behind cases, its primary and replica pods, and PostgreSQL services ending in rw (writes), ro (reads) and r.

6

Drift: delete Redis and watch it come backBastion

Delete the Redis application by hand — but leave its declaration in Git. Reconciliation compares what exists with what Git declares, and repairs the difference. This is why lasting changes are made in Git, never by hand.

kubectl --context tenant delete redis features
kubectl --context tenant get redis -w
✓

features returns within about a minute. Stop watching with Ctrl-C.

PART 2 Fraud scoring 25 min

Deploy the scorer into your own cluster, connect the switch to it through Kafka, add a small local language model that explains every block — then run the Part 0 attack again and watch it fail.

1

Deploy the scorer and connect the switchBastion · Switch VM

First hand the services the database password: Cozystack generated it on the platform side; this command copies the fraud user's password into a Secret in your cluster, where cases and dashboard read it. (The original README shows the full command with the generated value from your own Secret.) Then deploy the three fraud services. The scorer is deliberately small — CPU limit 500m — so Part 4 can push it past capacity.

cd ~/workshop
kubectl --context fraud -n fraud create secret generic cases-db \
  --from-literal=password="<from Secret postgres-cases-credentials>"

kubectl --context fraud apply -f manifests/02-scoring.yaml
kubectl --context fraud -n fraud get pods -w
✓

secret/cases-db created, then scorer, cases and dashboard all Running. Services reach the platform by names like kafka-kafka-kafka-bootstrap.tenant-austinNN.svc.cozy.local — your cluster is a tenant of the platform, on the same network.

The scorer is up, but nobody asks it anything yet. Confirm Kafka is READY True, enter the switch VM, point the switch at Kafka, and restart it:

kubectl --context tenant get kafka
virtctl console vm-instance-switch
# inside the VM (ubuntu / ubuntu):
sudo sed -i 's#^KAFKA_BOOTSTRAP=.*#KAFKA_BOOTSTRAP=kafka-kafka-kafka-bootstrap:9092#' /etc/auth-switch/env
cat /etc/auth-switch/env
sudo systemctl restart auth-switch
journalctl -u auth-switch -f
✓

“switch started in SCORING mode”, then “100 authorizations, 0 declined, stand-in 0.0%” (a little stand-in in the first seconds is just warm-up). Leave with Ctrl-] and open https://fraud.austinNN.workshop.aenix.io — about 20 authorizations a second, almost no declines, decision latency visible, Kafka lag near zero.

2

A language model explains every blocked paymentBastion

A decline needs a reason a support agent can read to the customer. Deploy the explainer: Qwen2.5 0.5B Instruct served by llama.cpp, running on CPU inside your cluster. The model weights come in; no card data goes out, and no external AI service is involved. The cases service already knows the explainer's address and has been waiting for it.

cat manifests/03-explainer.yaml
kubectl --context fraud apply -f manifests/03-explainer.yaml
kubectl --context fraud -n fraud rollout status deploy/explainer --timeout=5m
✓

“successfully rolled out” within a minute or two — the pod downloads a 400 MB model and loads it. If the wait times out, just run the rollout status command again.

3

Run the attack again — this time it failsBastion · Dashboard

Same job, same cards as Part 0. Keep the dashboard open while it runs.

CARD TESTING

Tiny probes, then a big buy

Three stolen cards make dozens of $0.50–$3.00 online payments to check they work, then try a big electronics purchase.

IMPOSSIBLE TRAVEL

Dallas, then Lagos in 2 minutes

A card used in Dallas is used in Lagos two minutes later — physically impossible for one cardholder.

BIN ATTACK

60 card numbers in a row

Sixty sequential card numbers from the same bank range (BIN), one dollar each — a guessing sweep.

kubectl --context fraud apply -f manifests/04-attack.yaml
kubectl --context fraud -n fraud logs job/attack -f
✓

Most payments are now declined. The first few probes of each card still pass — one tiny payment looks like any other; the pattern becomes clear after a handful. Card testing is stopped by about the sixth probe, a BIN attack by about the eighth card. On the dashboard, blocked transactions appear with reason codes, and within a minute or two each gets a plain-language explanation from the model — one by one, and occasionally clumsy: it is a very small model on one CPU. The rules and weights live in one short file: app/internal/scoring/rules.go.

PART 3 Grow the system with the catalog 30 min

Fraud analysts now want to run any query over every payment ever answered — without slowing the payment flow. So you add an analytics database beside the system, without touching it: ClickHouse reads the journal straight from Kafka, and reports land in an S3 bucket. The whole path is three catalog services and one SQL file, with no code of yours in between.

1

ClickHouse for the fraud analystsBastion · Git

Write platform/clickhouse.yaml from the ClickHouse docs: name analytics, one replica, one shard, 5Gi on replicated storage, preset t1.medium, user fraud with password Fraud2026 — and ClickHouse Keeper switched off, because a single node does not need it. Do not take t1.small: ClickHouse runs out of memory reading the payment journal.

Solution — platform/clickhouse.yaml 
apiVersion: apps.cozystack.io/v1alpha1
kind: ClickHouse
metadata:
  name: analytics
spec:
  replicas: 1
  shards: 1
  resourcesPreset: t1.medium
  size: 5Gi
  storageClass: replicated
  clickhouseKeeper:
    enabled: false
  users:
    fraud:
      password: Fraud2026
cd ~/fraud-infra
git add platform/clickhouse.yaml
git commit -m "Order ClickHouse for the analysts"
git push
✓

Wait until analytics shows ready in the dashboard before the next step.

2

Read the journal straight from KafkaBastion

Load manifests/05-analytics.sql into ClickHouse by piping it to the client inside the database pod. The file creates the three objects in the diagram above — a Kafka-reading table, a MergeTree store, and the materialized view between them. No application sits in between: ClickHouse reads Kafka directly.

cd ~/workshop
kubectl --context tenant exec -i chi-clickhouse-analytics-clickhouse-0-0-0 \
  -c clickhouse -- clickhouse-client --user fraud --password Fraud2026 \
  --multiquery < manifests/05-analytics.sql

# then ask your own questions interactively (exit to leave):
kubectl --context tenant exec -it chi-clickhouse-analytics-clickhouse-0-0-0 \
  -c clickhouse -- clickhouse-client --user fraud --password Fraud2026
SELECT merchant, count(*)
FROM payments
WHERE decision = 'DECLINE'
GROUP BY merchant
ORDER BY count(*) DESC
LIMIT 10;
✓

No errors from the load; the file's three example queries print at the end (possibly still empty right after loading). After a minute of catch-up: up to ten merchants with decline counts, most first. The other examples group declines by minute and reason, and show stand-in counts and shares per minute.

3

A bucket for reportsGit · Dashboard

Order a Bucket named reports with one user, analytics — straight into Git like everything else. A bucket user is not a person: it is a dedicated pair of S3 keys for this bucket only, stored by Cozystack in a Secret. ClickHouse writes reports with exactly those keys, and nothing else.

Solution — platform/bucket.yaml 
apiVersion: apps.cozystack.io/v1alpha1
kind: Bucket
metadata:
  name: reports
spec:
  users:
    analytics: {}
cd ~/fraud-infra
git add platform/bucket.yaml
git commit -m "Order a bucket for reports"
git push

When reports is ready, read its keys in the dashboard (Bucket → reports → Secrets → bucket-reports-analytics-credentials): you need accessKey, secretKey and bucketName. The endpoint s3.workshop.aenix.io is already in the query. Export the report from the ClickHouse client:

INSERT INTO FUNCTION s3(
  'https://s3.workshop.aenix.io/<bucketName>/daily-report.csv',
  '<accessKey>', '<secretKey>', 'CSVWithNames')
SETTINGS s3_truncate_on_insert=1
SELECT merchant, count(*)
FROM payments
WHERE decision = 'DECLINE'
GROUP BY merchant
ORDER BY count(*) DESC
LIMIT 10;
✓

daily-report.csv appears in the bucket UI at https://bucket-reports.austinNN.workshop.aenix.io. Journal → analytics → finished report, with zero code written by you.

PART 4 Production day 30 min

Three incidents, one after another: a traffic spike, a dead database node, and a server move under the running switch. Keep the fraud dashboard open the whole time — it is your window into all three.

1

Black Friday, with an autoscalerBastion · Dashboard

Write a HorizontalPodAutoscaler for the scorer: minimum 1, maximum 8 replicas, CPU target AverageValue 250m. Eight is the maximum useful number — auth.requests has eight partitions. Save it as ~/workshop/hpa.yaml (it belongs to your cluster, not the platform repo) and apply it. Then raise the traffic: the terminals read their rate from a ConfigMap, so no restart is needed.

Solution — hpa.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: scorer
  namespace: fraud
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: scorer
  minReplicas: 1
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: AverageValue
          averageValue: 250m
kubectl --context fraud apply -f hpa.yaml
kubectl --context fraud -n fraud patch configmap traffic -p '{"data":{"rate":"200"}}'
kubectl --context fraud -n fraud get hpa scorer -w
✓

Within a minute or two, stand-in jumps to 100% and the scoring queue grows — the single small scorer cannot keep up, so the switch decides alone and fraud would slip through. Then replicas climb 1 → 2 → 4 and, within about three minutes, stand-in falls back to a few percent. Afterwards, restore a normal day with rate 20; the HPA scales down by itself after about five minutes.

# back to a normal day:
kubectl --context fraud -n fraud patch configmap traffic -p '{"data":{"rate":"20"}}'
2

The primary database node goes downBastion · Dashboard

Find the primary of the PostgreSQL cluster, then delete its pod as if its server had died. --grace-period=5 just shortens the shutdown wait.

kubectl --context tenant get pods -l cnpg.io/cluster=postgres-cases -L role
kubectl --context tenant delete pod <the primary pod> --grace-period=5
kubectl --context tenant get pods -l cnpg.io/cluster=postgres-cases -L role -w
✓

Within seconds the replica becomes primary, and the deleted pod returns as the new replica. On the dashboard, the database panel shows “database unavailable” for a few seconds and the case queue grows — but payments are not affected: the switch never talks to the database. Its journal waits safely in Kafka.

kubectl --context fraud -n fraud logs deploy/cases --tail=20
✓

“database unavailable, holding … messages, retrying”, then the backlog is written. The dashboard's reconciliation line compares journaled vs. stored — within a minute or two it shows missing: 0. Not one case was lost.

3

The switch moves to another server, mid-flowBastion · Dashboard

The server under the switch needs maintenance. In a bank that usually means a 3 a.m. change window; here the VM live-migrates while it keeps answering terminals. Its memory is copied to the new server while it works, and the disk does not move at all — it sits on replicated storage both servers can reach.

kubectl --context tenant get vmi vm-instance-switch -o wide
virtctl migrate vm-instance-switch
kubectl --context tenant get vmim -w
kubectl --context tenant get vmi vm-instance-switch -o wide
kubectl --context fraud -n fraud logs deploy/terminals --tail=20
✓

The migration passes Pending → Scheduling → TargetReady → Succeeded within a minute, and the VM now runs on another node. On the dashboard, terminal errors stay at zero. For a second or two a few authorizations go unanswered while the network settles; terminals do what real terminals do — repeat the request with the same transaction id — and the dashboard counts them as “repeated by the terminal”.

After the workshop: Your environment stays with you for two weeks — bastion, cluster and dashboards keep working. Change the rules in rules.go, write a new attack, and use the same environment for the certification assignment the host shares at the end of the session.

If something goes wrong

The failures this workshop expects, and their fixes — straight from the original guide.

SymptomCause and fix
virtctl console shows nothingPress Enter — the login prompt is printed only once.
Switch log shows stand-in 100% after Part 2Kafka is not ready yet, or the address in /etc/auth-switch/env has a typo. kubectl --context tenant get kafka must show READY True.
Dashboard returns 502 or 503The dashboard pod is not running yet: kubectl --context fraud -n fraud get pods.
No explanations after the Part 2 attackThe explainer is still loading the model: kubectl --context fraud -n fraud logs deploy/explainer.
forbidden on a commandWrong context. Catalog services, VMs and PostgreSQL pods live in tenant; the fraud services live in fraud.
apply fails with SchemaError … unknown modelThe client-side check failed, not the cluster. Add --validate=false.
Git push rejectedRun git pull --rebase, then push again.
Flux is not applying a change / YAML errorkubectl --context tenant get kustomization platform shows the error; fix the file, commit, push.
ClickHouse: Memory limit exceededUse preset t1.medium, not t1.small.
